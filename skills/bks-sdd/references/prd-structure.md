# PRD Structure — BKS-SDD Reference

This document defines the canonical structure for PRDs generated by the bks-sdd skill.
The structure is derived from three sources:
- Spec-Driven Development Levels (SDD, Martin Fowler / Anthropic)
- Spec Review Checklist (BKS research base)
- Harness Engineering principles (Waldemar Neto / Dev Lab)

---

## Template

```markdown
# PRD — [Product / Feature Name]

**Status:** Draft | Review | Approved  
**Version:** 0.1  
**Owner:** [name or team]  
**Created:** [date]  
**Last updated:** [date]  

---

## 1. Problem Statement

What problem exists today? Who experiences it? What is the cost of not solving it?
Write 2–4 sentences. Be specific. Avoid marketing language.

## 2. Goal

What does success look like when this is done?
State one primary goal. Secondary goals may follow as a short list.

**Primary goal:** [one sentence]

**Secondary goals:**
- [goal 2]
- [goal 3]

## 3. Target Audience

Who uses this? Describe the user profile(s) relevant to this product or feature.
Include context about technical level, environment, and motivations if relevant.

## 4. Scope

### In scope
What this PRD covers. List the features, flows, or system areas included.

### Out of scope
What is explicitly excluded. This prevents scope creep during AI-assisted implementation.

## 5. Functional Requirements

List the behaviors the system must have. Write each as a testable statement.
Prefer "The system shall..." or "Users can..." over vague descriptions.

| # | Requirement | Priority (P0/P1/P2) | Notes |
|---|-------------|----------------------|-------|
| R1 | ... | P0 | |
| R2 | ... | P1 | |

## 6. Non-Functional Requirements

Constraints that cut across all features: performance, security, accessibility,
compliance, internationalization, offline support, etc.

| # | Constraint | Category | Acceptance Threshold |
|---|------------|----------|----------------------|
| NF1 | ... | Performance | |
| NF2 | ... | Security | |

## 7. User Scenarios

Describe 2–5 concrete usage scenarios. Each scenario should be a short narrative
that walks through a user achieving a goal. These become the basis for acceptance tests.

**Scenario 1 — [Name]**
> [User type] wants to [goal]. They [action]. The system [response]. They [outcome].

## 8. Architecture and Integration Boundaries

> **Para projetos .NET ou TypeScript com Arquitetura Hexagonal + TXC:** use as sub-seções §8a–§8d abaixo.  
> **Para projetos genéricos (sem Hexagonal/TXC):** descreva sistemas tocados, fronteiras de integração, APIs externas, bancos, auth e contratos de dados em forma livre.

### §8a — Internal Architecture

Fluxo obrigatório para projetos TXC:

```
Primary Adapter (HTTP/Worker)
  │ cria Transaction, popula campos de entrada (Hydrate)
  ▼
Primary Port: I{Entidade}Handler / I{Entidade}Query
  ▼
Handler / QueryHandler (Application layer)
  ├── Transaction.HydrateXxx(input)           → Fase 1: entrada
  ├── Aggregate.Create/Apply/Cancel(...)       → Fase 2: domínio
  ├── Transaction.HydrateXxxCriado(aggregate) → Fase 2: captura estado
  ├── IXxxRepository.SaveAsync(aggregate)     → Fase 3: persistência
  └── Transaction.FinalizeWith(aggregate)     → Fase 3: output
  ▼
PipelineResult<{Entidade}Response>
```

Não usar Steps numerados separados (ValidationStep, ProcessingStep) — são anti-padrão v1.

### §8b — Bounded Contexts e Aggregates

| Bounded Context | Aggregate Root | Primary Port (Command) | Primary Port (Query) |
|-----------------|----------------|------------------------|----------------------|
| [ex: Vendas]    | [ex: Pedido]   | [ex: IPedidoHandler]   | [ex: IPedidoQuery]   |

**Regra:** uma Primary Port de Command por BC (agrupa operações TXC do BC), uma Primary Port de Query por BC (agrupa todas as queries).  
**Nunca:** `ICreatePedidoUseCase`, `IListPedidosUseCase`, `ICancelPedidoUseCase` separados.

### §8c — Secondary Ports

| Secondary Port | Tipo | Serve a | Adapter previsto |
|----------------|------|---------|-----------------|
| [ex: IPedidoRepository] | Persistência | Aggregate Pedido | [ex: PostgreSqlPedidoRepository] |
| [ex: INotificacaoService] | Serviço externo | BoundedContext Vendas | [ex: SendGridNotificacaoAdapter] |

**Regra:** uma Secondary Port por aggregate ou recurso externo.  
**Nunca:** `IDBRepositoryPort` genérico, `IRepository<T>` genérico.

### §8d — External Integrations e ACL

Para sistemas externos com modelo de dados diferente do domínio, listar:

| Sistema externo | Secondary Port | ACL necessária? | Justificativa |
|-----------------|----------------|-----------------|---------------|
| [ex: API Correios] | [ex: ICalculadoraDeFrete] | Sim | Modelo externo não mapeia 1:1 com domínio |

> Para regras completas de Primary/Secondary Ports e Transaction Map, ver `references/txc-guidelines.md`.

## 9. Delivery Plan

Break the work into phases. Each phase must be independently deliverable and testable.
This structure directly feeds Phase 2 of the bks-sdd workflow (project breakdown).

| Phase | Description | Deliverable | Dependencies |
|-------|-------------|-------------|--------------|
| P1 | ... | ... | none |
| P2 | ... | ... | P1 |

## 10. Acceptance Criteria

How will we know the PRD has been successfully implemented?
List criteria that are binary: either met or not met.

- [ ] [criterion 1]
- [ ] [criterion 2]

## 11. Risks and Assumptions

What do we assume to be true that might not be? What could go wrong?

| Risk / Assumption | Impact | Mitigation |
|-------------------|--------|------------|
| ... | High / Med / Low | ... |

## 12. Open Questions

List any unresolved questions that must be answered before or during implementation.
Remove items as they are resolved. An empty section means the PRD is ready to execute.

- [ ] [question]

## 13. Sources

List every input used to generate this PRD: local files read, URLs fetched, and
any other references. This ensures traceability per the Spec Review Checklist.

- [file or URL]: [what it contributed]
```

## Field-by-field guidance

**Problem Statement (§1):** The most important section. If this is vague, the entire PRD
will drift. Push for specificity: who, what, why now.

**Scope (§4):** The "out of scope" list is as valuable as the in-scope list. Explicitly
bounding what is NOT included prevents AI agents from expanding implementation beyond intent.

**Functional Requirements (§5):** Write these só they can become test assertions.
"The system should be fast" is not a requirement. "Search results load within 300ms for
95% of queries" is.

**Architecture and Integration Boundaries (§8):** Use the conditional rule:
- If the project uses Hexagonal Architecture + TXC (.NET or TypeScript): fill §8a–§8d using the TXC-aware template. Read `references/txc-guidelines.md` before writing §8b and §8c. Primary Ports must be grouped by BoundedContext (not per CRUD operation). Secondary Ports must be specific per aggregate (not a generic `IDBRepositoryPort`).
- For other stacks or generic projects: describe systems touched, integration boundaries, external APIs, databases, and auth in free-form text.

**Delivery Plan (§9):** Each phase should be shippable. Avoid phases like "backend" +
"frontend" split — prefer vertical slices (a thin end-to-end piece of functionality).
This aligns with Spec-Driven Development's principle of iterative, verifiable increments.

**Open Questions (§12):** This is the harness feedback loop in written form. If a question
cannot be answered before development starts, flag it as a risk in §11 and document
the assumption being made.

**Sources (§13):** Required for traceability. Always list every file read and every URL
fetched. This is the link between the PRD and the research that produced it.

---

## SDD level targeting

This template supports all three SDD levels:

- **Spec-first:** Fill §1–§5 and §9. The spec guides implementation and may be retired after.
- **Spec-anchored:** Fill all sections. Keep the PRD updated as implementation progresses.
- **Spec-as-source:** Use the PRD as the canonical artifact; code is derived from it.

For most projects, target **spec-anchored** as the default.
